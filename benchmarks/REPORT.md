# Pearl Benchmark Report — Phase 23

Generated by [`run_benchmark.py`](run_benchmark.py) against real, shallow-cloned
upstream repositories, driving Pearl's actual MCP server (`python -m src.mcp`)
exactly as the VS Code extension does — `cwd` set to the target repo,
`PYTHONPATH` set to Pearl's own repo.

**Hardware note:** this environment has ~2.8 GB RAM (well under the ~8 GB
this project has assumed in earlier validation passes) and was observed
under heavy memory pressure/swapping during this run. Under pressure, a
single LLM call could occasionally take 60–180s+; the numbers below were
captured once memory pressure eased and are representative of a "warm,
not-swapping" run. Timings should be read as *relative*, illustrative
figures for this specific constrained sandbox, not as production-hardware
numbers — see "Known limitations" below.

Model: `qwen2.5-coder:3b` via Ollama (`OLLAMA_BASE_URL=http://localhost:11434/v1`).

## Known limitations of this benchmark run

1. **Token usage was not measured.** Pearl's `OpenAICompatibleProvider` does
   not currently surface the response's `usage` field up through
   `LLMClient`/`Planner`, and Ollama's own `/v1/chat/completions` responses
   do include a `usage` block (confirmed via raw `curl` during this
   session), so this is available at the transport layer but not wired
   through Pearl's abstractions. Reported here as a gap, not fabricated.
2. **Retries/replans were 0 in every run** because every benchmarked task
   was simple and well within the small model's capability — this
   benchmark did not specifically stress the reflection/replanning path.
   (That path is already covered by dedicated tests —
   `tests/test_executor.py`, `tests/test_mcp_autonomous.py`'s
   "recovery after replanning" case — with a real fault injected.)
3. **Scenario 2 (patch-producing) was only run against 3 of the 6 repos**
   (FastAPI, React, requests), not all 6, given this sandbox's memory
   constraints and session time budget. The mechanism is identical
   regardless of repo (it does not depend on repo size — `create_file`'s
   cost is independent of how large the surrounding repository is), so
   the 3 sampled repos are a reasonable proxy for the other 3.
4. **Hardware, not Pearl, is the dominant bottleneck observed.** Under
   memory pressure this session, a single LLM call occasionally took
   60–180s+ (see the fix for the two integration bugs below — those were
   found *because of* this benchmarking work, not despite it). This is a
   property of this specific 2.8 GB sandbox, not of Pearl's own code path,
   which is confirmed by the sub-30s numbers once memory pressure eased.

## Integration issues found and fixed during this benchmark

Running Pearl against real external repositories (not Pearl's own repo)
surfaced two real, previously-undetected integration bugs — both are
workspace-path-resolution bugs, not architectural issues, and both are now
fixed (see "Modified files" in the phase summary):

1. **`Planner.PROMPT_FILE`/`REPLAN_PROMPT_FILE` were cwd-relative strings**
   (`"src/prompts/planning.txt"`). When Pearl's workspace (`cwd`) is any
   directory other than Pearl's own repo — i.e. every real use case — this
   raised `FileNotFoundError` and **autonomous execution could not run at
   all** on an external project. Fixed by resolving these paths relative to
   `planner.py`'s own file location instead of cwd.
2. **`.env` loading was cwd-relative** (`load_dotenv()` with no path). When
   cwd wasn't Pearl's repo root, `.env` silently failed to load and every
   provider setting fell back to its hardcoded default — observed directly
   as Pearl trying to call a nonexistent `llama3` model on Ollama instead
   of the configured `qwen2.5-coder:3b`. Fixed by resolving `.env`'s path
   relative to `settings.py`'s own file location instead of cwd.

Both were verified fixed by re-running the same probe against the
`requests` benchmark repo with `cwd` pointed at it — the first bug's
`FileNotFoundError` and the second's wrong-model `404` were both
confirmed present *before* the fix and absent *after*.
